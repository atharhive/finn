3. Architecture on TrueForge

The extension is a client of local TrueForge 0.185.0; TrueForge owns model calls, the tool loop and session/turn state. Finn registers a per-connection, loopback HTTP MCP server with bearer authentication, creates an inline agent and renders streamed events. Provider credentials remain in TrueForge, never in Finn or the repository.

Editor capabilities exposed as MCP tools are assemble_context, read_file, search_workspace, propose_edit and run_command. Proposed replacement content stays in memory. A human reviews and accepts individual hunks before source writes; undo protects against overwriting later edits. Terminal commands require separate explicit human approval and run as the local user, not in a security sandbox.

Approval is currently enforced by Finn's editor boundary, not TrueForge tool-approval events. The default agent enables TrueForge compaction and disables sandbox, memory and web search; optional configured skills can require a sandbox. Meaningful use of compaction/skills must be demonstrated in the final session before any top-anchor claim. Cancellation requests remote cancellation and discards pending proposals without undoing edits already accepted by the human.

4. How context is selected

Finn builds a guarded inventory, excludes secret/ignored/out-of-workspace inputs, and passes a private sanitized snapshot to the Rust repository/dependency optimizer. It adds task-term scoring, resolves explicit @file/@symbol mentions and packs selected excerpts under the configured budget (default 8,000 estimated tokens). Selected paths, reasons and warnings are returned to the agent; Task B must visibly show automatic discovery, not prompt-supplied filenames.

The budget is a conservative estimate, not an exact tokenizer guarantee. Lexical and dependency signals are cheap and explainable but can miss semantically relevant code. Context selection is separate from the model's own context-window compaction; neither a configured budget nor a template is proof of live behaviour.

8. Known limitations and what you would do with another month

The live-model acceptance gate remains open. Preparation was exercised against the official full SHA and upstream tests/test_cli.py returned 58 passed. The pristine repository correctly failed Task A's off/n/docstring probes and Task B's command/edit-count probes. Current trade-offs include approximate token accounting, lexical retrieval blind spots, local-only infrastructure, pending real-world provider testing and approval at the editor boundary rather than harness-driven review. Approved terminal commands can write files; isolation and deliberate approval remain essential. Pending proposals are not durable across restart. Ignored files/Git internals are excluded from the C hash audit.

With another month we would complete repeated model-backed acceptance across independent providers, measure latency/retrieval quality, improve symbol/dependency ranking and indexing, test long-session compaction, deepen harness-native approval integration, and add cross-platform packaging/host coverage. These are proposed improvements, not completed capabilities.
